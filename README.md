# NextIDE

NextIDE is a local-first, capability-oriented coding IDE.

[![CI](https://github.com/leviseek/ai-code/actions/workflows/ci.yml/badge.svg)](https://github.com/leviseek/ai-code/actions/workflows/ci.yml)

## Workspace status

The repository currently contains the first Phase 0 vertical slice:

- Rust workspace
- transactional document model
- undo/redo
- snapshot/recovery primitives
- minimal CLI smoke path
- headless Desktop Shell with window, input, command-palette, notification, and file-tree pipelines
- incremental file-tree rendering with structured change batches and events
- task runtime with lifecycle events, summaries, cancellation, timeout, cleanup, and task queries
- VFS read-only, typed file metadata queries (`exists` returning `io::Result<bool>` plus `is_file`/`is_dir`/`metadata` returning `FileKind` + `FileMetadata` with kind/len/readonly): `exists` reports `Ok(true)` for existing entries and `Ok(false)` for missing ones, and rooted filesystems reject path escapes with `Err(PermissionDenied)` instead of silently reporting `false`; missing entries report `Ok(false)` from `exists`/`is_file`/`is_dir` and `NotFound` from `metadata`
- VFS typed, stable-sorted directory enumeration (`read_dir` returning `io::Result<Vec<FileEntry>>` with name/path/kind/len): entries sort by name in stable order, missing paths report `NotFound`, non-directory paths report `NotADirectory`, and root escapes keep reporting `PermissionDenied`; the trait default returns `Unsupported`, so existing `FileSystem` implementations (`LocalFileSystem`, `MemoryFs`, `TreeFs`, `NoopFs`) compile and behave unchanged, and `LocalFileSystem::list` now delegates to `read_dir`
- dependency-free workspace text search (`search` module: `SearchQuery`/`SearchOptions`/`SearchMatch`/`SearchMatcher`, entry points `search::search(fs, &query)` and `query.run(&fs)`): recursively walks `read_dir` over any rooted `FileSystem`, reports every matching line (relative path, 1-based line, byte column, line text), skips binary (invalid UTF-8 or NUL-containing) and unreadable/denied files and subdirectories silently, propagates only search-root errors, stably sorts results by `(path, line, column)`, and truncates to `max_results`; `case_sensitive` (default on), `max_depth` (default 64) and a normalized `"."` root keep paths inside the workspace root and walks finite even through symlinked cycles; matching is pluggable through the reusable `SearchMatcher` — `SearchQuery::new` keeps the plain literal-substring behavior, while `SearchQuery::glob` (or `matcher: SearchMatcher::Glob`) interprets the needle as a simple glob pattern (`*` = any run of characters, `?` = exactly one character), a deliberately non-regex wildcard matcher with no character classes, alternation, anchors, or escapes
- minimal, dependency-free Git status capability (`git` module: `GitStatusEntry`/`GitFileState`/`GitStatusCode`/`GitStatusSnapshot`, entry point `git::status(root) -> io::Result<GitStatusSnapshot>`): runs `git -C <root> status --porcelain=v1` through `std::process::Command` (no shell, the root is a single argument), parses every XY status code (`M`/`T`/`A`/`D`/`R`/`C`/`U`/`?`/`!`, unknown codes preserved as `Unknown`), keeps rename/copy pairs as `path` (current) plus `original` (source), decodes git's C-style quoted paths (`"with space \344\270\255\346\226\207.txt"` → `with space 中文.txt`), and returns entries stably sorted by path; root safety: the root must exist (`NotFound`) and be a directory (`NotADirectory`), a missing `git` binary surfaces as `NotFound`, a non-zero git exit (e.g. "not a git repository") surfaces as `Other` with git's stderr in the message, and any parsed path that is absolute or contains a `..` component is rejected with `InvalidData` so a snapshot can never name a path outside the repository; per porcelain v1 semantics paths are relative to the repository top level, so when `root` is the repository top level (the normal workspace case) every reported path is relative to `root` exactly
- minimal Git diff query (`git` module: `GitDiffLine`/`GitDiffLineKind`/`GitDiffHunk`/`GitDiffFile`/`GitDiffSnapshot`, entry point `git::diff(root, path: Option<&Path>) -> io::Result<GitDiffSnapshot>`): runs `git -C <root> diff --no-ext-diff --unified=3` (worktree vs index, no external diff driver, 3 context lines), parses the unified output into files sorted stably by path, each with its hunks and lines (`GitDiffLine` records context/added/removed kind, 1-based old/new line numbers, and the line text; `GitDiffFile` carries the current `b/` path — decoded from git's C-style quoting — plus a `binary` flag for `Binary files ... differ` entries, which carry no hunks); the optional `path` is passed to git as a pathspec after `--` and must be rooted at `root` — relative, non-empty, and free of `..`, root and drive components, otherwise `InvalidInput` before git is spawned; root/exit/parse error behaviour matches `status` (`NotFound`/`NotADirectory`/`Other` with git's stderr/`InvalidData`), and because plain `git diff` exits 0 whether or not differences exist, a non-zero exit always means a real failure; unlike porcelain, diff line *content* is not UTF-8 validated — invalid bytes become U+FFFD (git quotes paths but never content) — while every parsed path still passes the same escape-rejecting safety check as `status`
- minimal Git stage and commit capability (`git` module: `git::stage(root, paths: &[&Path]) -> io::Result<GitStatusSnapshot>` and `git::commit(root, message) -> io::Result<GitCommitResult>`, with `GitCommitResult { hash, summary }` where `hash` is the full 40-character object id read back via `git rev-parse HEAD` and `summary` is the git-defined subject via `git log -1 --format=%s`): `stage` runs `git -C <root> add -- <paths>` (no shell; every path is its own argument after the `--` separator, so option-like names such as `--help`/`-f` are staged literally) and returns the fresh `GitStatusSnapshot` from `git::status`; every stage path is validated before git is spawned — non-empty, relative, free of `..`/root/drive components, and not `:`-prefixed (git pathspec magic such as `:(top)`/`:(exclude)`) — and an empty `paths` slice is rejected, all with `InvalidInput`; `commit` rejects empty/whitespace-only messages and NUL bytes with `InvalidInput` before spawning and runs `git -C <root> commit --message=<message>` (the message is a single argument, never shell-interpreted, so `--amend`-looking text is committed verbatim); error behaviour matches `status`/`diff` (`NotFound`/`NotADirectory`/`Other` with git's message — taken from stderr, falling back to stdout, because `git commit` prints failures like "nothing to commit" there), and existing `status`/`diff` behaviour is unchanged
- minimal safe Git unstage capability (`git` module: `git::unstage(root, paths: &[&Path]) -> io::Result<GitStatusSnapshot>`): runs `git -C <root> reset -- <paths>` (no shell; every path is its own argument after the `--` separator, so option-like names such as `--help`/`-f` are un-staged literally) and returns the fresh `GitStatusSnapshot` from `git::status`; every path is validated before git is spawned with the same rules as `stage` — non-empty, relative, free of `..`/root/drive components, and not `:`-prefixed (git pathspec magic) — an empty `paths` slice is rejected, all with `InvalidInput`, and a `.` pathspec un-stages everything under `root`; unlike `git add`, a `git reset` pathspec that matches nothing is a no-op (exit 0), so un-staging a path that is not staged (or does not exist) succeeds and the returned snapshot always reflects the resulting state; error behaviour matches `status`/`diff`/`stage`/`commit` (`NotFound`/`NotADirectory`/`Other` with git's message), and existing `status`/`diff`/`stage`/`commit` behaviour is unchanged
- minimal safe Git branch query and checkout capability (`git` module: `GitBranch`/`GitBranchSnapshot`, entry points `git::branches(root) -> io::Result<GitBranchSnapshot>` and `git::checkout(root, branch) -> io::Result<GitStatusSnapshot>`): `branches` runs `git -C <root> for-each-ref --format=%(HEAD)|%(refname:short) refs/heads` (no shell; git's own machine-oriented `%(HEAD)` atom emits `*` for the checked-out branch and a space otherwise, and names are split on the first `|`, so no human-format parsing is involved) and returns every local branch stably sorted by short name, each as a `GitBranch { name, current }` — a detached HEAD marks no branch as current, and every parsed name still passes the same escape-rejecting check as status paths; `checkout` validates the branch name before spawning — non-empty, free of NUL bytes, not absolute and without `..` components, and not `-`-prefixed, so it can never be parsed as a git option (`--` cannot shield it because `git checkout --` turns the argument into a pathspec instead of a branch) — then runs `git -C <root> checkout <branch>` with the name as a single argument and returns the fresh `GitStatusSnapshot` from `git::status`; error behaviour matches `status`/`diff`/`stage`/`commit` (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message), and existing `status`/`diff`/`stage`/`commit` behaviour is unchanged
- minimal safe Git restore and stash capability (`git` module: entry points `git::restore(root, paths: &[&Path]) -> io::Result<GitStatusSnapshot>` and `git::stash_push(root, message: Option<&str>) -> io::Result<GitStatusSnapshot>`): `restore` discards the named paths' *worktree* changes with `git -C <root> restore -- <paths>` (no shell; every path is its own argument after the `--` separator and validated exactly like stage/unstage paths — non-empty, rooted at `root`, not `:`-prefixed — so option-like names such as `--help`/`-f` are restored literally, and an empty `paths` slice is rejected with `InvalidInput`); `git restore` writes the worktree from the index by default, so staged changes are kept, untracked files are never deleted (a pathspec matching an untracked file is a git error surfaced as `Other`), and unstaged deletions are re-created; `stash_push` moves the repository's *tracked* changes (staged and unstaged) into a new stash entry with `git -C <root> stash push [--message=<message>]` — the optional message follows the commit rules (non-empty after trimming, no NUL bytes, else `InvalidInput`) and travels as a single `--message=<message>` argument so `--amend`-looking text is recorded verbatim — and a stash push with nothing to stash is a no-op (git exits 0 with "No local changes to save"), while untracked files are never stashed; both return the fresh `GitStatusSnapshot` from `git::status`, and the module docs document the dangerous-operation boundaries: `restore` is destructive and irreversible (a `.` pathspec discards every unstaged change under `root`), and `stash_push` rewrites the whole repository's worktree — from a nested `root` it also stashes changes outside `root`, and stash entries are recoverable via `git::stash_apply`/`git::stash_pop` (see the stash-management bullet below); error behaviour matches the other operations (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout` behaviour is unchanged
- minimal safe Git stash management (`git` module: `GitStashEntry`/`GitStashSnapshot`, entry points `git::stash_list(root) -> io::Result<GitStashSnapshot>`, `git::stash_apply(root, index: usize) -> io::Result<GitStatusSnapshot>` and `git::stash_drop(root, index: usize) -> io::Result<GitStatusSnapshot>`): `stash_list` runs `git -C <root> stash list` (no shell) and parses each `stash@{N}: <description>` line into a typed entry — the entry's `index` (the `stash@{N}` ref number, 0 = most recent) and its `description` (the text after the prefix: the recorded message for entries created by `stash_push`, otherwise git's default `WIP on <branch>: <abbrev> <subject>` line) — stably sorted by index ascending, with malformed lines rejected as `InvalidData`; `stash_apply` runs `git -C <root> stash apply stash@{index}` where the ref is formatted from the caller-supplied index into a single argument (never parsed as an option), and before git is spawned the index is validated against a fresh `stash_list`, so an out-of-range index is `InvalidInput` instead of a git error; a successful apply *keeps* the entry (unlike `git stash pop`), and plain `git stash apply` (no `--index`) restores the changes into the worktree without reinstating the staged/unstaged split; `stash_drop` runs `git -C <root> stash drop stash@{index}` with the same index validation and permanently deletes the entry (git renumbers the rest); both return the fresh `GitStatusSnapshot` from `git::status`; error behaviour matches the other operations (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message — an apply that conflicts with the current worktree leaves conflict markers and fails with `Other` — /`InvalidData`), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push` behaviour is unchanged
- minimal safe Git stash pop capability (`git` module: `git::stash_pop(root, index: usize) -> io::Result<GitStatusSnapshot>`): applies entry `stash@{index}` with `git -C <root> stash pop stash@{index}` (no shell; the ref is formatted from the caller-supplied index into a single argument, so it can never be parsed as an option) and drops it on success — git's own apply-plus-drop safety: the entry is removed only after a successful apply, so a pop that conflicts with the current worktree fails with `Other` carrying git's message and leaves the entry in place (with conflict markers in the worktree), never silently deleting a stash; the index is validated against a fresh `stash_list` before git is spawned exactly like `stash_apply`/`stash_drop`, so an out-of-range index is `InvalidInput` instead of a git error; on success the entry is dropped (git renumbers the rest) and the changes are restored into the worktree without reinstating the staged/unstaged split, like plain `stash_apply`; returns the fresh `GitStatusSnapshot` from `git::status`; error behaviour matches the other operations (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message/`InvalidData`), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop` behaviour is unchanged
- minimal safe Git commit amend capability (`git` module: `git::amend(root, message) -> io::Result<GitCommitResult>`): replaces the current HEAD commit with `git -C <root> commit --amend --message=<message>` (no shell; the message is a single `--message=<message>` argument exactly like `commit`, so option-like text such as `--amend` is recorded verbatim) and returns the same `GitCommitResult` as `commit` — the fresh HEAD hash via `git rev-parse HEAD` and the git-defined subject via `git log -1 --format=%s` — reusing `commit`'s message validation (empty/whitespace-only or NUL messages are `InvalidInput` before git is spawned) and its result parsing; the amend never opens an editor and rewrites the last commit in place (the parent is kept, staged changes are folded in, the hash always changes), so it is a history rewrite that must only be applied to commits that have not been published; error behaviour matches `commit` (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message, e.g. "You have nothing to amend." for a repository without commits), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop` behaviour is unchanged
- minimal safe Git history query (`git` module: `GitCommitEntry`/`GitLogSnapshot`, entry point `git::log(root, limit: Option<usize>) -> io::Result<GitLogSnapshot>`): runs `git -C <root> log --format=%H%x00%P%x00%an%x00%aI%x00%s --date=iso-strict` (no shell; fields are NUL-separated by git itself and records are newline-terminated, so parsing is machine-oriented) and returns each commit as a `GitCommitEntry { hash, parents, author, date, subject }` in git's own output order — newest commit first, never re-sorted — where `parents` is empty for a root commit and holds one hash per parent for a merge; `limit` caps the query itself (`--max-count=n`) and the snapshot, `Some(0)` short-circuits to an empty snapshot without spawning git, and `None` returns the whole history; parsed output is validated before it is trusted — the output must be valid UTF-8, every record must have exactly the five fields with a non-empty author and date, and every hash (commit and parent) must be non-empty hexadecimal, otherwise `InvalidData`; root/exit error behaviour matches `status` (`NotFound`/`NotADirectory`/`Other` with git's message — a repository without any commits makes `git log` itself fail with "does not have any commits yet"), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend` behaviour is unchanged
- minimal safe Git tag query (`git` module: `GitTag`/`GitTagSnapshot`, entry point `git::tags(root) -> io::Result<GitTagSnapshot>`): runs `git -C <root> for-each-ref --format=%(objectname)%00%(refname:short) refs/tags` (no shell; git's own machine-oriented output — NUL-separated fields, newline-terminated records) and returns every tag stably sorted by short name, each as a `GitTag { name, object }` where `object` is the full object id git reports — for a lightweight tag the id of the object it names (typically a commit), for an annotated tag the id of the tag object itself, recorded without expanding the tag to its target; parsed output is validated before it is trusted — valid UTF-8, exactly two fields per record, a non-empty hexadecimal object, and a non-empty name that passes the same escape-rejecting check as status paths, otherwise `InvalidData`; error behaviour matches `status`/`branches` (`NotFound`/`NotADirectory`/`Other` with git's message), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend`/`log` behaviour is unchanged
- minimal safe Git tag create/delete capability (`git` module: entry points `git::tag(root, name) -> io::Result<GitTagSnapshot>` and `git::delete_tag(root, name) -> io::Result<GitTagSnapshot>`): `tag` creates a *lightweight* tag with `git -C <root> tag -- <name>` (no shell; the name is a single argument and the `--` separator shields it from option parsing) and `delete_tag` removes a tag with `git -C <root> tag --delete <name>`; both return the fresh `GitTagSnapshot` from `git::tags`, and both are strictly local — the worktree and the index are never touched; every name is validated before git is spawned — non-empty, free of NUL bytes, not `-`-prefixed, relative and free of `..` and empty components (no leading, trailing or doubled `/`), and free of control characters, whitespace and git's other ref-forbidden characters (`~`, `^`, `:`, `?`, `*`, `[`, `\`, `@{`, leading-dot components, `.lock`-suffixed components, trailing dots) — mirroring `git check-ref-format` while allowing one-level names such as `v1.2` and slash names such as `feature/v1.2`; error behaviour matches the other operations (`NotFound`/`NotADirectory`/`InvalidInput`/`Other` with git's message — an existing tag for `tag`, an unknown tag for `delete_tag` —/`InvalidData`), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend`/`log`/`tags`/`remotes` behaviour is unchanged
- minimal read-only Git remote query (`git` module: `GitRemote`/`GitRemoteSnapshot`, entry point `git::remotes(root) -> io::Result<GitRemoteSnapshot>`): runs `git -C <root> remote -v` (no shell) and is strictly read-only — it only reads the local Git configuration, never contacts a network and never fetches or pushes; git's own machine-oriented `name<TAB>url (fetch|push)` lines are parsed into one `GitRemote { name, fetch_url, push_urls }` per remote — `fetch_url` from the `(fetch)` line (`remote.<name>.url`, `None` when the remote has no fetch URL, in which case git prints a bare `name<TAB>` line) and `push_urls` from the `(push)` lines in git's order (a remote without an explicit `remote.<name>.pushurl` reports its fetch URL as the single push URL, and a multi-valued `pushurl` yields one entry per value) — stably sorted by name; URLs are kept exactly as git prints them (they may contain spaces and are never interpreted as paths or passed back to git); parsed output is validated before it is trusted — valid UTF-8, every line must be `name<TAB>url (fetch)`, `name<TAB>url (push)` or the bare `name<TAB>` form, every name must be non-empty, free of whitespace and pass the same escape-rejecting check as status paths, and a remote may carry at most one fetch line, otherwise `InvalidData`; error behaviour matches `status`/`tags` (`NotFound`/`NotADirectory`/`Other` with git's message), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend`/`log`/`tags` behaviour is unchanged
- minimal safe Git remote management (`git` module: entry points `git::add_remote(root, name, url) -> io::Result<GitRemoteSnapshot>`, `git::set_remote_url(root, name, url) -> io::Result<GitRemoteSnapshot>` and `git::remove_remote(root, name) -> io::Result<GitRemoteSnapshot>`): `add_remote` registers a new remote with `git -C <root> remote add <name> -- <url>`, `set_remote_url` rewrites an existing remote's fetch URL with `git -C <root> remote set-url <name> -- <url>` (without `--push`, so an explicit `remote.<name>.pushurl` is kept untouched), and `remove_remote` deletes a remote with `git -C <root> remote remove <name>`; each returns the fresh `GitRemoteSnapshot` from `git::remotes`. All three are strictly local — they only read or write the repository's Git configuration, never contact a network, perform a fetch or a push, or touch the worktree or the index; no shell is involved and every name and URL travels as a single argument, with the `--` separator shielding the URL of `add_remote`/`set_remote_url` from option parsing, so even a URL that starts with `-` is stored literally. Names and URLs are validated before git is spawned — a name must be non-empty, free of NUL bytes and whitespace, not `-`-prefixed, and free of `..` and of absolute or drive components; a URL must be non-empty and free of NUL bytes (spaces are allowed and stored raw) — otherwise `InvalidInput`; a name that already exists (for `add_remote`) or does not exist (for `set_remote_url`/`remove_remote`) surfaces as `Other` with git's message; error behaviour otherwise matches `remotes` (`NotFound`/`NotADirectory`/`Other`/`InvalidData`), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend`/`log`/`tags`/`remotes` behaviour is unchanged
- minimal read-only Git remote lookup (`git` module: entry points `git::remote_url(root, name) -> io::Result<GitRemote>` and `git::remote_exists(root, name) -> io::Result<bool>`): both run the same strictly local `git -C <root> remote -v` query as `git::remotes` — no shell, no network access, no fetch or push — and reuse its parsing and validation; `remote_url` returns the `GitRemote` whose name matches, and a validly named remote that is not configured surfaces as `NotFound` with the name in the message (unlike `set_remote_url`/`remove_remote`, which let git report it); `remote_exists` returns `Ok(true)` exactly when the parsed snapshot contains the name and `Ok(false)` for a validly named but absent remote, while root/git-binary/git-exit/parse errors are reported exactly as `remotes`; both validate `name` before git is spawned with the same rules as the remote-management operations (empty/NUL/whitespace/`-`-prefixed/`..`/absolute-or-drive names are `InvalidInput`), and existing `status`/`diff`/`stage`/`unstage`/`commit`/`branches`/`checkout`/`restore`/`stash_push`/`stash_list`/`stash_apply`/`stash_drop`/`stash_pop`/`amend`/`log`/`tags`/`remotes`/`tag`/`delete_tag`/`add_remote`/`set_remote_url`/`remove_remote` behaviour is unchanged

- minimal, dependency-free Git status adaptation for the shell UI (`git_status` module in `nextide-shell`, a pure trait/model layer that never modifies the kernel): `status_kind` classifies a kernel `GitFileState` (`XY` columns) into a typed `StatusKind` (`Conflicted`/`StagedAndUnstaged`/`Staged`/`Unstaged`/`Untracked`/`Clean` — untracked wins over conflicts, two-sided changes beat one-sided ones, and ignored states classify as `Clean` since `status` never reports them), `StatusKind::marker` gives every kind a stable single-character visual badge (`!` conflict, `M` modified on both sides, `S` staged, `U` unstaged, `?` untracked, single space for clean), `tree_statuses` maps a `GitStatusSnapshot` into one `TreeStatus` per entry (path, kind, raw state, and the `original` source path for renames/copies, with `is_rename_or_copy`) re-stably-sorted by path so the model's ordering is its own contract, `summary` derives the status-bar counts (`GitStatusSummary`: total plus staged/unstaged/untracked/conflicted — two-sided entries count toward both staged and unstaged, conflicts are their own bucket, a clean snapshot is all zeros with `is_clean()`, and `From<&GitStatusSnapshot>` is provided), and `marker_for` looks up one path's marker for tree-row badges; `GitStatusAdapter` is the mapping contract with default methods delegating to the free functions, and `DefaultGitStatusAdapter` is the ready-to-use unit implementation; no new dependencies
- Git status markers wired into the shell tree (`nextide-shell`, minimal integration — the kernel is untouched and the shell never runs git): `TreeItem` and `TreeRenderRow` each carry a `status: StatusKind` field (defaulting to `Clean`; `TreeRenderRow` additionally carries `status_marker`, the stable `StatusKind::marker()` badge projected alongside the kind in `tree_rows`/`render_tree`), `ShellSnapshot` exposes `git_summary: Option<GitStatusSummary>` for the status bar, and `DesktopShell::update_git_status(snapshot: GitStatusSnapshot)` applies an externally supplied kernel status snapshot so the next `snapshot()` and rendered rows show each path's marker plus the summary counts — file nodes by exact path (`marker_for`, so an entry whose path equals the node marks it), directory nodes by the aggregated status of everything below them (`aggregate_directory_status`, the most severe descendant kind, or the directory's own entry when it has one, for example a submodule; a directory with no changed entry under it stays `Clean`, as do clean paths and paths absent from the snapshot); because `TreeRenderRow` participates in `diff_tree_rows` equality, a marker change surfaces as an `Updated` row change (with its `status_marker`) through the usual `workspace.tree.changed` events; `DesktopShell::clear_git_status()` is the inverse of `update_git_status` — it detaches the applied snapshot and returns to the pre-integration default (every marker `Clean`, `git_summary` `None`, `git_status_text()` `None`, so a host switching away from a Git workspace can report "Git integration inactive" again instead of a misleading `Some("clean")`, and the marker-clearing change surfaces as `Updated` rows just like applying markers); all constructors (`DesktopShell::new`, `ShellSnapshot::from_context`, `tree_rows`) keep their signatures and existing fields, and behaviour without a git snapshot is unchanged (every row `Clean`/`" "`, `git_summary` `None`)
- Git status-bar summary text projection (`nextide-shell`, pure model layer — no GPU, no real drawing): `GitStatusSummary::summary_text()` (also available as the free function `summary_text` and as the `GitStatusAdapter::summary_text` default, so adapters observe the same text) projects the summary counts into one stable, documented status-bar string — `"clean"` when nothing is pending, `"changed: staged=<n> unstaged=<n> untracked=<n>"` when changes exist but no entry is unmerged, and `"conflicted: conflicted=<n> staged=<n> unstaged=<n> untracked=<n>"` when any entry is unmerged (conflicts outrank ordinary changes) — always emitting every key with the same names, order and single-space separators, so the text is parseable and never changes between releases; `ShellSnapshot` exposes the projection through the accessor `git_status_text() -> Option<String>` (`Some` exactly when `git_summary` is `Some` — `Some("clean")` means Git integration is active with a clean repository — `None` while no Git snapshot has been applied); no new dependencies and all existing fields, constructors and behaviour are unchanged
- Git directory status aggregation for the file tree (`nextide-shell`, pure model layer — never runs git): `aggregate_directory_status(statuses: &[TreeStatus], directory: &Path) -> Option<StatusKind>` (also a `GitStatusAdapter::aggregate_directory_status` default delegating to the free function) aggregates every `TreeStatus` whose path is the directory itself (for example a submodule entry) or a component-wise descendant of it (via `Path::starts_with`, so `src/lib.rs` belongs to `src` while `src2/lib.rs` and `src-file.rs` do not; the empty path aggregates the whole repository) into one directory-badge kind — the most severe kind among the matching entries, using the enum's documented `Ord` severity order (conflicts outrank two-sided changes, which outrank one-sided changes, which outrank untracked; `Clean` entries carry no badge and are ignored, so a directory whose matching entries are all clean aggregates exactly like an empty one) — or `None` when no changed entry is under the directory, mirroring `marker_for`'s optional contract; renames/copies count by their current path only, so the disappearing `original` path is not re-marked (consistent with `tree_statuses`/`marker_for`); the projection is pure and deterministic — it never executes git and never depends on iteration order; `aggregate_directory_status` composes with `tree_statuses` (aggregate over `&tree_statuses(snapshot)`) and is re-exported from the crate root; all existing fields, functions and behaviour are unchanged
- minimal, dependency-free Git diff adaptation for the shell UI (`git_diff` module in `nextide-shell`, a pure trait/model layer that never modifies the kernel, never runs git and adds no dependencies): `file_views` maps a kernel `GitDiffSnapshot` into one `DiffFileView` per file (current `b/` path as `PathBuf`, `binary` flag, `hunks: Vec<DiffHunkView>` in output order) re-stably-sorted by path so the model's ordering is its own contract (equal paths keep input order); every `DiffLineView` preserves the kernel's 1-based `old_line`/`new_line` and maps `GitDiffLineKind` to a typed `DiffLineKind` (`Context`/`Added`/`Removed`) with stable `as_str()` labels and stable single-character gutter markers (`' '`/`'+'`/`'-'`); `DiffFileView` derives per-file counts (`added_lines`/`removed_lines`/`context_lines`/`line_count`/`hunk_count`/`is_binary`); `summary` derives the status-bar counts (`DiffSummary`: files, binary_files, added, removed, context — binary and metadata-only changes count as files but never as lines, with `is_clean()`, `total_lines()` and `From<&GitDiffSnapshot>`); `summary_text` projects a summary into one stable parseable status-bar string (`"clean"` when every bucket is zero, otherwise `"changed: files=<n> added=<n> removed=<n> context=<n> binary_files=<n>"` with fixed keys in fixed order); `file_view_for` looks up one file's view by path; `GitDiffAdapter` is the mapping contract with default methods delegating to the free functions, `DefaultGitDiffAdapter` is the ready-to-use unit implementation, and the whole API is re-exported from the crate root (`diff_summary`/`diff_summary_text` are the root aliases, so they never collide with the status layer's `summary`/`summary_text`); no new dependencies
- pure-model diff line text rendering for the shell UI (`git_diff` module in `nextide-shell` — no GPU, no real drawing, no new dependencies): `DiffLineView::display_text()` renders each line as the stable `"<marker> <text>"` string (single-character kind marker, one space, then the line text — context lines render with two leading spaces, added lines with `+`, removed lines with `-`, and blank lines keep their marker plus one trailing space; the exact string is the contract); `DiffHunkView::display_header()` returns the raw `@@` hunk header exactly as git printed it (section headings preserved); `DiffFileView::file_label()` renders the file's path with `/` separators — rebuilt from the path components, so the label is identical on every platform even though the stored path is a platform-native `PathBuf` — plus a `" (binary)"` suffix for binary files, the only suffix, so labels are parseable with `strip_suffix`; all three formats are fixed and documented, and all existing fields, constructors and behaviour are unchanged
- pure-model Git diff panel state for the shell UI (`git_diff_panel` module in `nextide-shell` — builds on the `git_diff` model layer, no GPU, no real drawing, no new dependencies, and all existing APIs and behaviour are unchanged): `DiffPanelSnapshot` holds the projected `DiffFileView`s of a kernel `GitDiffSnapshot` (built with `from_snapshot`, or `from_views` with ready-made views — both enforce the model's stable path order and start every file **expanded** with nothing selected), tracks per-file expansion, and keeps a stable selection over the visible lines; `toggle_file(path) -> bool` expands/collapses one file (unknown paths are no-ops returning `false`, files with equal paths share one expansion key, and `is_expanded(path)` observes the state); `visible_lines() -> Vec<&DiffLineView>` is the stable visible line list — every line of every expanded file in model/hunk/line order, with binary and metadata-only files contributing no lines, identical across repeated calls and unaffected by toggling other files — and the selection is an index into that list: `select_next`/`select_prev` move and clamp at the ends (from no selection, next picks the first visible line and prev the last; with nothing visible the selection stays clear), while `toggle_file` re-clamps the selection so it always names a visible line (collapsing every file clears it); `selected_line()`/`selected_file()`/`selected_index()` observe the state; `summary()` derives the whole-snapshot `DiffSummary` from the views — identical to `diff_summary` of the same snapshot and deliberately unaffected by expansion; `render_lines() -> Vec<String>` is the stable text projection of the panel (every file renders its `file_label()` line first — also when collapsed, so collapsed files stay visible and togglable — and expanded files then render each hunk's `display_header()` followed by each line's `display_text()`; repeated calls return identical lines and toggling one file only removes or restores that file's block, while collapsing never changes `summary()`), and `visible_text()` is the same lines joined with `'\n'` (every rendered line is a single physical line, so splitting recovers `render_lines()` exactly); `Default` is the empty panel; the type is re-exported from the crate root (`DiffPanelSnapshot`)
- minimal pure-model diff panel commands wired through shell commands and input (`nextide-shell`, no GPU, no real drawing, never runs git, no new dependencies, all existing commands/keys/input keep their behaviour): `DesktopShell` now holds an optional `diff_panel: Option<DiffPanelSnapshot>` (new by default, so every diff command is a no-op until a panel is applied) and `update_diff_panel(snapshot: GitDiffSnapshot)` injects an externally supplied kernel diff snapshot — the shell never runs git itself; the pure state interface (`toggle_diff_file(path) -> bool`, `diff_next_line() -> bool`, `diff_prev_line() -> bool`) delegates to the panel and reports whether state actually changed (false without a panel, for unknown toggle paths, or when the selection is clamped at an end); three registered commands drive the panel — `diff.toggle-file <path>` (an empty path resolves to the selected tree path, so the `Ctrl+T` binding toggles the file the user is looking at), `diff.next-line` and `diff.prev-line` — reachable through the palette (`command_from_id`), the keymap (`Ctrl+J` next, `Ctrl+K` prev, `Ctrl+T` toggle), and a new `UiInput::ClickDiffFile(path)` for clicking a diff file row; every applied mutation publishes one stable `diff.panel.changed` event (`action=toggle,file=<path>,expanded=<bool>` / `action=select,index=<n>` / `action=select,index=none`) through the usual observable execution path (`shell.command.executed`); `ShellSnapshot` exposes `diff_summary: Option<DiffSummary>` (projected from the panel, so it is `None` while no panel is active) plus the `diff_status_text()` accessor with the same `Some`-exactly-when-active semantics as `git_status_text`; all constructors, fields and behaviours without a diff panel are unchanged

Task state and summary APIs are available through `TaskManager::state`, `summary`, `summaries`, and `ids`; pending tasks can be removed and terminal tasks can be cleaned with lifecycle events.

Capability metadata is observable through `CapabilityRegistry::ids`, `iter`, `summary`, and `summaries`: iteration and projections are returned in stable, sorted id order, and `CapabilitySummary` is a cloneable, UI-safe snapshot of a capability's id, version, and declared permissions. `is_empty`/`len`/`contains` remain available for cheap registry checks.

Shell command metadata is observable through `command_ids`, `get_command`, `command_summary`, and `command_summaries`: ids enumerate in stable declaration order, and `CommandSummary` is a cloneable, UI-safe snapshot of a command's id, title, and search keywords, decoupled from the static `COMMANDS` descriptor table so the command palette, UI, and plugins can observe commands without borrowing. `search_commands`/`command_id`/`COMMANDS` remain unchanged.

Shell command execution is observable through `CommandExecutionResult`, `CommandOutcome`, and `CommandError`: `DesktopShell::execute_observed` runs a `ShellCommand` and returns a typed, cloneable record (stable command id, tri-state outcome, structured error) that UI and plugins can consume without borrowing. Every execution publishes a `shell.command.executed` event with a stable payload (`id=<id>,outcome=<outcome>` or `id=<id>,outcome=failed,error=<kind>,message=<message>`); failures keep publishing `shell.command.failed` plus an error notification. `command_title`, `is_registered`, and `describe_execution` resolve execution results back to registered command metadata, and `CommandError`/`CommandErrorKind` classify failures (`io`, `not-found`, `invalid-state`, `unknown`) with a message, round-tripping through `std::io::Error`. Existing `execute`, `execute_checked`, `execute_selected`, and `CommandResult` signatures and behavior are unchanged; the checked/selected paths now route through the observable one, so every executed command also emits `shell.command.executed`.

## Development

```powershell
cargo test --workspace
cargo run -p nextide-cli -- smoke
cargo run -p nextide-cli -- bootstrap
cargo run -p nextide-cli -- task-smoke
```

`task-smoke` exercises the background task runtime: it registers a cross-platform echo command (`cmd.exe /C echo` on Windows, `sh -c printf` elsewhere), spawns it through `TaskManager::spawn_async`, polls `AsyncTaskHandle::wait_timeout` within a finite deadline, and prints the task's status and output, panicking on failure or timeout.

Background async tasks can also be bridged to a caller-owned `EventBus`: `TaskManager::spawn_async_with_sink` / `spawn_async_timeout_with_sink` accept an `AsyncTaskEventSink`, and the UI thread polls the matching `TaskEventReceiver` (e.g. each frame) and replays what it consumed into the `EventBus` with `publish_into` — so the background worker never holds the non-thread-safe bus, while the async task's lifecycle and output still surface as `task.*` events.

The editor kernel is the single source of truth for document mutations. UI, AI, collaboration, and extensions must eventually submit changes through the same transaction API.

## Packaging

A minimal Windows packaging baseline lives in [`packaging/windows/`](packaging/windows/README.md). It does exactly two safe things and nothing more:

1. builds the release binaries: `cargo build --release`
2. stages the CLI and Desktop Shell executables under `dist/windows/`

[`packaging/windows/manifest.json`](packaging/windows/manifest.json) is the single source of truth for the product metadata, target architecture, artifact list, and verification strategy (exists-and-sha256); `build.ps1` loads, validates, and enforces it. `product.version` must equal the `[workspace.package]` version declared in the root `Cargo.toml` (the workspace's single version source — every member crate inherits it via `version.workspace = true`); `build.ps1` enforces the match by a read-only text parse of `Cargo.toml` (no `cargo` invocation, no dependencies) and fails before building or staging on any mismatch. The manifest target block is enforced the same way: `target.os` / `target.architecture` / `target.triple` must equal the pinned packaging target `windows` / `x86_64` / `x86_64-pc-windows-msvc` (mutually consistent), so a stale or cross-arch manifest can never stage artifacts for the wrong platform. The manifest `release` block carries the release metadata and is validated read-only too: `release.license` and `release.publisher` must be non-empty and `release.release_channel` must be exactly `stable` or `beta` (anything else — or a missing/blank field — fails before building or staging). It is metadata only: no signing and no installer.

```powershell
powershell -ExecutionPolicy Bypass -File packaging\windows\build.ps1
```

The script verifies the release build succeeds, validates the manifest, checks that `product.version` matches the Cargo.toml workspace version, checks that the manifest target block matches the pinned packaging target `x86_64-pc-windows-msvc`, checks the release block read-only (`license`/`publisher` required, `release_channel` must be `stable` or `beta`), checks that every manifest artifact exists before copying, and after staging verifies each staged copy matches its release binary by size and SHA-256, then reports the staged files' size and SHA-256. It then writes a `SHA256SUMS.txt` checksum manifest into `dist/windows/` — one `<hash>  <file>` line per staged artifact, in manifest order, LF line endings (GNU `sha256sum -c` compatible) — built from the verified staged hashes and re-verified by parsing it back, so the checksum file that ships is proven consistent with the staged files. The manifest's `stage.checksum_file` names the checksum file (committed value `SHA256SUMS.txt`) and is validated read-only: it must be a plain leaf name that does not collide with any artifact file. The script deliberately performs no dangerous operations — no cleaning/deleting, no registry changes, no signing, no installation, no writes outside the repository. `dist/` is generated output and is git-ignored. CI runs the packaging job — self-test first, then build + stage — after the checks pass (see [CI](#ci)); installer and signing are later phases (see `STATUS.md`).

The baseline is self-tested by [`packaging/windows/test-build.ps1`](packaging/windows/test-build.ps1) — a zero-framework PowerShell suite that runs `build.ps1` against throwaway sandbox copies under `%TEMP%` (the real repository is never modified) and covers the `-SkipBuild` happy path (including the generated `SHA256SUMS.txt` checksum manifest and its exact per-file hashes) plus every failure mode: missing manifest, missing artifact, wrong pinned hash, path escapes (`..` and rooted paths), invalid JSON, file-name mismatch, unsupported schema version, a failed release build, a `product.version`/Cargo.toml workspace-version mismatch, a missing root `Cargo.toml`, a `Cargo.toml` without a `[workspace.package]` version, manifest target mismatches against the pinned `x86_64-pc-windows-msvc` packaging target (`target.architecture`, `target.triple`, and `target.os`), release-metadata violations (missing `release` block, blank `license`/`publisher`/`release_channel`, and a `release_channel` other than `stable`/`beta` — plus a passing `beta` case), and `stage.checksum_file` violations (a path separator, and a name colliding with an artifact file — plus a passing custom-name case). It also proves pre-existing files in `dist\windows\` are preserved (the script only overwrites, never deletes):

```powershell
powershell -ExecutionPolicy Bypass -File packaging\windows\test-build.ps1
```

The suite exits `0` when all 26 tests pass and `1` otherwise.

Consumers can verify any staged directory — the repository's own `dist/windows/` or a downloaded release artifact — with [`packaging/windows/verify-checksums.ps1`](packaging/windows/verify-checksums.ps1): it reads the `SHA256SUMS.txt` checksum manifest and proves every line parses (`<hash>  <file>`), every named file exists, every hash matches the actual file, and the directory matches the manifest exactly. It is strictly read-only (no writes, never executes the files it verifies, no dependencies, no network) and exits non-zero on any failure. Its sandboxed self-test suite is [`packaging/windows/test-verify-checksums.ps1`](packaging/windows/test-verify-checksums.ps1) — 14 cases covering the happy path, a bad hash, a missing file, a malformed line, missing/empty manifests, path-escaped and duplicate entries, an extra unlisted file, GNU-style lowercase hashes, CRLF line endings, a custom checksum file name, and a read-only proof — and CI runs both the verifier (right before the dist upload) and its test suite (as a pre-packaging gate):

```powershell
powershell -ExecutionPolicy Bypass -File packaging\windows\verify-checksums.ps1
```

End users can run the whole download → checksum → smoke flow against a
published GitHub Release with one command:
[`packaging/windows/verify-release-download.ps1`](packaging/windows/verify-release-download.ps1)
(`-Tag v0.1.0`): it downloads the release's two binaries and the
manifest-declared checksum file, resolves the checksum file name from the
release's own `manifest.json` (`stage.checksum_file`, never a hardcoded
default), asserts the tag is exactly `v<product.version>`, re-verifies the
download read-only with `verify-checksums.ps1` (fetched from the same tag) and
smoke-tests the downloaded CLI — the same two gates CI runs against the exact
bytes it publishes; any failure exits non-zero and says not to run the
binaries. Downloads are restricted to `https://` and `file://` URLs only —
`http` and any other scheme are refused (the checksum manifest and the
consumer verifier travel over the same URLs, so an unauthenticated transport
would let a network attacker substitute binaries and manifest together). The
"never write into the repository" rule refuses download folders that resolve
to the repository root or its staging folder (`dist/`); the protected root is
derived from the script's own location by default (only trusted when the
script really sits in `packaging/windows` of that checkout, otherwise the
script fails and asks for it) and can be stated explicitly with
`-RepositoryRoot` — e.g. when running a copy of the script. Its
sandboxed self-test suite is
[`packaging/windows/test-verify-release-download.ps1`](packaging/windows/test-verify-release-download.ps1)
(26 cases over `file://` URLs — no network, never touches the repository),
and CI runs it as a pre-packaging gate. See the
[packaging README](packaging/windows/README.md) for the full end-user guide.

## CI

GitHub Actions CI (`.github/workflows/ci.yml`) runs on a `windows-latest` runner, since the project targets Windows, and gates every push and pull request with the same three checks that are verified locally:

- `cargo fmt --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`

The workflow installs only the stable Rust toolchain (with `rustfmt` and `clippy` components); the workspace has no external dependencies and nothing else is downloaded.

A second job, `packaging-windows`, runs only after the checks pass (`needs: ci` — a failing check stops the run before packaging starts). It explicitly verifies the packaging manifest in all four required areas — manifest validity, `product.version` vs the Cargo workspace version, the target block vs the pinned `x86_64-pc-windows-msvc` packaging target, and the release metadata (`license`/`publisher`/`release_channel`) — plus the `stage.checksum_file` checksum manifest name — twice, with no duplicated logic. First it runs the sandboxed packaging self-test `packaging/windows/test-build.ps1` as a pre-packaging gate (its 26 cases run `build.ps1` against a throwaway `%TEMP%` sandbox — the repository is never touched — and a failing test stops the run before anything is built), alongside a second gate running `packaging/windows/test-verify-checksums.ps1` (14 sandboxed cases for the consumer-side checksum verifier, including a read-only proof), then it builds the release binaries with `cargo build --release` and stages them into `dist/windows/` with `packaging/windows/build.ps1 -SkipBuild`, which re-runs the same read-only manifest/version/target/metadata/checksum-file validation against the committed `manifest.json` and the real `Cargo.toml`, then verifies each staged artifact by size and SHA-256 and writes the manifest-declared checksum manifest (`stage.checksum_file`, committed value `SHA256SUMS.txt`) from the verified hashes (re-verifying it by parsing it back). The staged CLI binary is then smoke-tested end to end (`.\dist\windows\nextide-cli.exe smoke` — the editor-kernel smoke flow, which panics on any failure), proving the artifact that ships actually runs, not just that it hash-matches its source. The staged directory is uploaded as a channel-suffixed workflow artifact: right after checkout the job reads `release.release_channel` and `stage.checksum_file` from the committed manifest (read-only local parse, no network, same `stable`/`beta` and non-blank rules `build.ps1` enforces) and uploads `dist/windows` as `nextide-windows-dist-<channel>` (the upload fails if the directory is empty), so stable and beta runs can never overwrite each other's artifact. Immediately before that upload a dedicated gate runs the repository's consumer-side verifier `packaging/windows/verify-checksums.ps1` read-only against the exact `dist/windows` directory about to be uploaded, passing the manifest-declared checksum file name (`stage.checksum_file`, resolved right after checkout) via `-ChecksumFile` (no dependencies, no network) — every line must parse as `<hash>  <file>`, every named file must exist, every entry's hash must equal the actual file, and the directory must match the manifest exactly (no missing, corrupt, extra or duplicate entries) — so the checksum manifest that ships inside the dist artifact is proven correct, not just present. The same resolved channel names a companion **release-metadata artifact**: the committed `packaging/windows/manifest.json` is uploaded as `nextide-windows-manifest-<channel>` alongside the binaries, carrying the validated product identity, pinned target, release metadata (license / publisher / release_channel) and artifact list that produced this release, so later release/publish steps can consume the exact single source of truth without re-deriving anything. Immediately before that manifest upload a lightweight gate re-reads the exact file about to be uploaded with PowerShell's built-in `ConvertFrom-Json` (no dependencies, no network, no cargo invocation) and re-asserts the validated identity inline — the file must parse as valid JSON, `schema_version` must be 1, product name/version must be present, the target block must equal the pinned packaging target, the release metadata must be valid with a `release_channel` of exactly `stable`/`beta` that also matches the channel resolved for the run, and the artifact list must be non-empty — so the uploaded manifest is proven valid JSON and consistent with the manifest the pipeline validated. `dist/` is git-ignored, so the artifact is how the packaged binaries reach later release/publish steps.

A third job, `release`, completes the chain: on a version-tag push only (`refs/tags/v*`, `if:` condition; it never runs for branches or pull requests), it turns the artifacts the `packaging-windows` job just uploaded into an actual GitHub Release. Right after checkout it runs a sandboxed release-job simulation gate (`packaging/windows/test-release-sim.ps1`, 27 zero-framework cases against throwaway `%TEMP%` sandboxes — no network access, no GitHub Release ever created, the repository never touched): it proves the tag/version rejection rules (the pushed tag must be exactly `v<product.version>` — v-prefixed semver with no leading zeros in any numeric segment, the channel exactly `stable`/`beta`, every violation — non-v/malformed/leading-zero/pre-release tags, mismatched versions, invalid channels, blank versions, invalid/missing manifests — rejected), the four-file release file manifest (both binaries, the manifest-declared checksum file and `manifest.json` present, non-empty, checksum- and artifact-list-consistent, and byte-identical to the committed manifest) and the publish step's attachment naming (the exact file list handed to the GitHub CLI, with the checksum entry built from the resolved `stage.checksum_file` — never a hardcoded default) before anything is downloaded or published. It runs only after `packaging-windows` (`needs: packaging-windows`), downloads the same channel-suffixed `nextide-windows-dist-<channel>` and `nextide-windows-manifest-<channel>` artifacts of that run, and — with no rebuild, no re-staging and no recomputed checksums — re-verifies the downloaded bytes with the repository's consumer-side verifier (`packaging/windows/verify-checksums.ps1 -DistDir dist/windows -ChecksumFile dist/windows/<stage.checksum_file>`, the same script dist consumers use, with the checksum file name resolved from the committed manifest — never hardcoded) and smoke-tests the downloaded `nextide-cli.exe` before anything is published. It also proves the downloaded `manifest.json` is byte-identical to the committed manifest the pipeline validated (SHA-256 compare) and asserts the final consistency link of the chain: the pushed tag must be exactly `v<product.version>` (e.g. `v0.1.0`), where `product.version` is the manifest version the packaging job already proved equals the `[workspace.package]` version in the root `Cargo.toml` — so a release can never be tagged with a version the artifacts do not claim. The release is then created with `gh release create` (the runner's preinstalled GitHub CLI) under the pushed tag, attaching both release binaries, the manifest-declared checksum file (`stage.checksum_file`, committed value `SHA256SUMS.txt`) and the validated `manifest.json` release metadata; the job's token is scoped to the minimum (`contents: write` to create the release, `actions: read` to download the artifacts). If a release for the tag already exists, `gh` fails and the job fails — releases are never silently overwritten. Usage: push a `v<version>` tag matching the manifest version to trigger the whole pipeline and publish the release, e.g. `git tag v0.1.0 && git push origin v0.1.0`.

See the [workflow status](https://github.com/leviseek/ai-code/actions/workflows/ci.yml) for current runs.
